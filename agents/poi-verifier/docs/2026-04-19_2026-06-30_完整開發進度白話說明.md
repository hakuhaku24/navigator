## 階段一：專案開站、畫面雛形（4/19 ～ 4/21）

- 用 Next.js 把專案骨架搭起來，接上 Supabase 資料庫（一開始就建了 13 張表，並開啟 pgvector
  這個「向量搜尋」擴充功能，為後面的語意搜尋鋪路）。
- 做出第一版視覺風格（海洋藍＋珊瑚橘 → 後來改成深森林綠），蓋出首頁、建立行程的三步驟表單、
  加入行程頁面等基本頁面。
- 做出手機版「底部導覽列」和桌面版「側邊欄」雙軌導覽。
- 寫出**Token 投票系統**：每人有固定的「必去票」「否決票」「喜歡」可以投，左右滑動景點卡片決定
  要不要納入行程，投完票會自動算出排行榜，否決的景點會被劃掉沉到最底下。
- 做出一版「天氣應變」畫面的模擬版（先用假資料展示「下雨要不要換景點」的概念，給後面真正的應變
  系統當參考）。
- 寫了 45 筆景點的демо資料（北海岸、陽明山、東北角各 15 筆），這份資料後來變成整個專案早期
  最重要的「測試用景點庫」。
- 做了一些小修正：景點圖片連不上的問題（改用穩定的圖庫網站）、Dashboard 快捷按鈕、景點總覽頁。

## 階段二：專案重整、景點驗證 Agent 開發起步（4/30 ～ 5/8）

- 把專案資料夾重新整理：畫面設計稿移到 `prototypes/`，新增專門放「景點驗證 AI」的
  `agents/poi-verifier/` 資料夾，分工更清楚。
- 開始寫**景點驗證 Agent**：給它一個景點名稱，它會自動去網路上找資料，交叉比對好幾個來源，
  判斷「這個景點是不是真的存在、資料新不新」，並且算出一個「可信度分數」。
- 過程中修了很多細節錯誤，包括：
  - 防止「同名但不同地點」的景點被誤判成同一個（加入座標距離比對）。
  - 修正「只有部落格提過一次」就被當成「景點存在」的誤判邏輯。
  - 改善搜尋方式（改用 DuckDuckGo，加 Serper 當備援），並調整各種來源的可信度權重。
  - 修正日期判讀、分數計算等多個小 bug。
- 寫了 `batch-verify.ts`，可以一次把 45 筆景點全部送去驗證，不用一筆一筆手動跑。
- 整理了教授給的回饋、組員討論紀錄，以及一些題目發想文件，作為後續方向的依據。

## 階段三：應變系統 Agent + 向量資料庫上線（5/12 ～ 5/22）

- 寫出**應變系統 Agent**（領航者的另一顆核心大腦）：當天氣變差、景點關閉等突發狀況發生時，
  它會自動：① 偵測事件 → ② 評估「值不值得換」→ ③ 篩選掉不合格的候補景點 → ④ 排序找出最佳替代
  方案 → ⑤ 用 AI 寫成一段話跟使用者說明建議。
  - 真的接上中央氣象署的天氣 API，不是假資料。
  - 雨天會優先考慮室內景點、景點關閉會優先考慮營業時間夠長的，邏輯會依事件類型調整。
  - 主要用 Gemini，故障時自動切換到 Claude，確保系統不會掛掉。
- 把景點資料「向量化」存進資料庫（白話講：讓電腦能用「意思相近」而不是「關鍵字完全相同」的方式
  找景點，例如搜尋「下雨天室內文青景點」也能找到合適的地方）。
- 把資料庫架構重新設計成「全部行程群組共用同一份景點知識庫」，而不是每個揪團都要重存一份，這樣
  搜尋效率和資料一致性都更好。
- 修了幾筆假資料、優化向量品質（讓 embedding 同時包含官方資訊和部落格真實心得，搜尋更準）。
- 補了 API 費用試算文件、環境變數設定指南，方便組員自己架設開發環境。

## 階段六：景點可信度查證升級——P0/P1/P2（6/4 ～ 6/17）

這部分要解決的問題是：**怎麼知道一個景點的資料是真的、是新的？** 不能只信任單一來源，所以加了
三個新的「查證管道」：

- **官網查證**：自動搜尋景點官網，確認真的存在、內容真的相關，找不到就老實回報「沒有」，不會
  捏造網址。
- **PTT 查證**：自動搜尋 PTT 上的旅遊版討論，抓最新文章日期，知道「這個景點是不是還有人在去」。
- **YouTube 查證**：自動搜尋相關影片，並且**過濾掉業配影片**，只看真實旅客分享。

同時寫了一份評估報告，比較「YouTube / IG / PTT / Dcard / 官網」各管道的有效性、成本、法律風險。
這三個管道也都用 45 筆景點資料做過完整批次測試，確認結果合理可用。

之後把這些查證結果接進資料庫：搜尋用的文字描述現在會包含真人在 PTT、官網上講過的話，讓「下雨天
岩石濕滑」這種口語化搜尋也能命中對應景點。也新增了一支「結構化 RAG」示範腳本，示範 AI 回答時如何
標明資料出自文件的哪一段，回答更精準。

⚠️ 這裡有一步**還沒執行**：因為 Supabase 免費方案會自動休眠，需要有資料庫管理權限的組員去後台
喚醒專案，才能把這批新查證資料正式寫入資料庫。

## 階段七：接上 TDX 政府開放資料（6/25 ～ 6/30，含今天準備推送的修改）

**TDX 是什麼**：交通部「觀光資料平台」，裡面有政府整理好的全台景點資料。用它來補足手 key 45 筆
之外的景點，省去自己一筆一筆找資料的工夫。

1. **接上 TDX**：寫好欄位對照文件、自動匯入程式，能把 TDX 資料抓下來轉換格式存進資料庫。同時
   加了「混合搜尋」功能（語意搜尋＋關鍵字搜尋並用，準確度更高）。
2. **發現真實資料有問題、重新規劃**：跑過真資料後發現 TDX 的「縣市」欄位常常是錯的（記的是
   管轄單位不是實際位置）、「關鍵字分類」欄位幾乎全空、電話號碼格式很髒。重新寫了一份「施工圖」
   文件記錄這些修正方式。
3. **蓋一個「資料清洗工廠」**：寫了共用模組，專門把上述髒資料洗乾淨（推算真實縣市、清洗電話、
   整理圖片分類），並做了 60 項測試全數通過。
4. **接上既有流程**：把清洗工廠接上 TDX 匯入流程，讓資料存進資料庫前先清洗修正。這部分組員自述
   「比較複雜」，先寫文件交接給大家接續。
5. **今天接續完成**：解決了組員卡住的問題（同一個欄位在「手 key 45 筆」和「TDX 資料」裡代表的
   意思不一樣，新增判別方式分辨），把電話、營業時間、城市、分類等資料從大雜燴欄位升級成 9 個正式
   的資料庫欄位，並刻意「新舊並存」不影響其他人寫好的功能，確認所有既有測試（58~98 項不等）都
   還是全部通過。準備好但**還沒套用到資料庫**、等大家確認沒人在同時跑舊版匯入程式後就會推送的
   檔案：
   - 新的資料庫欄位設定檔
   - TDX 匯入程式的小修正
   - 入庫核心程式的修改
   - 施工圖文件的進度更新
6. **補測「沒有自動測試覆蓋到」的部分**：發現負責「把資料寫進資料庫」的核心程式
   （`ingestToDB`）一直以來都沒有任何自動測試碰過。原本想拿真資料庫測，但發現 Supabase 連不上
   （見下一點），改用「假裝資料庫」的臨時腳本：攔截掉真正會發送網路請求的地方（寫入資料庫、呼叫
   Gemini 算向量），改成接住資料印出來檢查，不需要連線、不花 API 額度。分別模擬「TDX 來源」和
   「手寫 45 筆來源」兩種情境，9 個新欄位跟原本的 `metadata` 欄位結果都跟設計時預期的完全一致，
   驗證完臨時腳本就刪掉了。仍然沒辦法測到的部分：資料庫設定檔套用到真實資料庫時會不會出錯、
   寫入後欄位內容讀出來是否正確——這兩項要等 Supabase 連線恢復才能驗證。
7. **發現 Supabase 連不上，而且比「休眠」更嚴重**：原本以為只是免費方案自動休眠，但實際檢查
   發現資料庫網址連 DNS 都解析不出來（用 Google 的公開 DNS 查也是「查無此網域」）。這跟單純休眠
   不一樣——休眠通常網址還連得到、只是顯示「已暫停」；現在這種「網址根本不存在」的狀況，比較
   可能是專案被刪除或網址換掉了，需要有後台管理權限的組員盡快確認，不是喚醒就能解決。
