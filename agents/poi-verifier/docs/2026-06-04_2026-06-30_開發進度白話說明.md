## 第一部分：景點資料「可信度」怎麼來的（6/4 ～ 6/17）

這部分要解決的問題是：**怎麼知道一個景點的資料是真的、是新的？** 我們不能只信任單一來源，所以陸續
加了三個新的「查證管道」：

### 1. 三個新查證管道（6/4）

- **官網查證**：自動搜尋景點的官方網站，確認網站真的存在、內容真的跟這個景點有關（不會亂猜一個
  網址就當真，找不到就老實回報「沒有」，不會捏造）。
- **PTT 查證**：自動搜尋 PTT 上 travel / Hiking / Taipei 三個版有沒有人討論過這個景點，抓最新一篇
  文章的日期，藉此知道「這個景點是不是還有人在去」。
- **YouTube 查證**：自動搜尋 YouTube 上的相關影片，並且會**過濾掉業配影片**，只看真實旅客的分享。

同時也寫了一份分析報告，評估「YouTube / IG / PTT / Dcard / 官網」這幾種查證方式，哪個有效、要花多少
錢、有沒有法律風險（例如某些平台不能隨便爬資料）。

並且用我們手 key 的 45 筆景點資料，把這三個查證管道**全部跑過一輪測試**，確認真的能用、結果合理。

### 2. 把測試結果寫成 TODO、補齊細節（6/4、6/16）

- 整理出「demo 前要做」和「demo 後再做」的後續工作清單，方便排優先順序。
- 把 YouTube 查證管道也做了一次完整的 45 筆批次測試（結果：45 筆裡有 39 筆找到非業配的真實影片）。

### 3. 把三個查證結果「真正存進資料庫」、做 RAG 展示（6/17）

- 前面查到的官網摘要、PTT 文章標題，現在會被加進景點的「語意描述」裡一起存進資料庫。**白話講**：
  以前搜尋「下雨天岩石濕滑」這種口語化的描述，系統找不到對應景點；現在因為真人在 PTT/官網上講過
  類似的話，系統存了這些真實語句，搜尋時就比較容易命中。
- 新增一支整合腳本，可以把三個查證管道的結果合併、一次性匯入資料庫，不用每次都重新跑一次完整驗證
  （省下大量等待時間）。
- 新增一個「結構化 RAG」的示範腳本，示範如何讓 AI 在引用文件內容時，**知道這段話是出自文件的哪一章
  哪一節**，回答會更精準（用我們的 `CLAUDE.md` 當示範文件）。
- ⚠️ 這次有一步**還沒執行**：因為 Supabase（資料庫）的免費方案會自動休眠，需要有資料庫管理權限的
  組員去後台把專案喚醒，才能把這批新查證資料正式寫入資料庫（指令已經寫好，預計約 9 分鐘）。

## 第二部分：接上 TDX 政府開放資料（6/25 ～ 6/30）

**TDX 是什麼**：交通部「觀光資料平台」，裡面有政府整理好的全台景點、餐廳、旅宿資料（名稱、地址、
電話、營業時間、照片等）。我們用它來補足手 key 45 筆之外的景點資料，省去自己一筆一筆找資料的工夫。

### 1. 一開始：把 TDX 資料「接上」我們的系統（6/25、6/26）

- 寫了一份對照文件，把「TDX 的資料長相」和「我們系統需要的資料長相」做一一對應。
- 寫了一支自動匯入程式，可以呼叫 TDX 的 API，把景點資料抓下來、轉換格式、存進我們的資料庫。
- 也順便加了「混合搜尋」功能（同時用語意搜尋＋關鍵字搜尋找景點，準確度更高）。

### 2. 發現問題、重新規劃（6/29、6/30）

寫程式跑過真實的 TDX 資料後，發現原本的規劃有幾個問題對不上：
- TDX 給的「縣市」欄位常常是錯的（例如某景點寫「新北市」，但它其實在宜蘭）—— 因為那欄位記的是
  「管轄單位」不是「實際位置」。
- TDX 的「關鍵字/分類」欄位幾乎都是空的，不能依賴。
- 電話號碼格式很髒（重複國碼之類的）。

所以重新寫了一份「施工圖」文件，把這些真實狀況的修正方式都寫清楚，作為後續所有人接續開發的依據。

### 3. 蓋一個「資料清洗工廠」（6/30）

針對上面發現的問題，寫了一個共用的「正規化模組」，專門負責把髒資料洗乾淨，包括：
- 用「郵遞區號 → 地址 → TDX縣市」這個優先順序，推算出**真正**的縣市（比直接用 TDX 給的縣市準確）。
- 清洗電話號碼格式。
- 整理圖片、分類等欄位。

這個模組寫好後也做了完整測試（60 項測試全部通過），確保它不會出錯。

### 4. 把清洗工廠接上既有流程（6/30）

把上面那個「資料清洗工廠」實際接上 TDX 匯入的流程，讓景點的縣市、電話這些欄位在存進資料庫之前都先
經過清洗、修正。這部分組員自己也留言說「這方面比較複雜」，做到一半先寫了文件交接，請大家接續完成。

### 5. 今天接續完成的部分（尚未送出，等確認後 commit）

組員卡住的地方是：我們資料庫裡的景點資料，目前「電話、營業時間、地址縣市、分類」這些欄位都是塞在
一個大雜燴的欄位（`metadata`）裡面，不是獨立的正式欄位，這樣以後要篩選、排序會比較麻煩。組員想把
它們升級成獨立欄位，但卡在一個技術問題：同一個欄位在「手 key 的 45 筆資料」和「TDX 資料」裡代表的
意思不一樣（一個是策展分區，一個是真實縣市），不知道怎麼分辨。

我們今天：

1. **解決了這個卡住的判斷問題**（用「這筆資料有沒有 TDX 編號」來分辨它的來源，藉此決定欄位該
   怎麼填）。
2. **新增了 9 個正式的資料庫欄位**（分類、城市、郵遞區號、策展分區、營業時間、電話、圖片、官網、
   資料更新時間），讓以後查資料更方便、更快。
3. 刻意設計成「新舊並存」——原本大雜燴欄位裡的資料完全不動，只是「多存一份」到新欄位，這樣才不會
   讓其他人寫好的功能（例如下雨備案系統）突然壞掉。
4. 確認所有既有測試（58~98 項不等）都還是全部通過，沒有弄壞東西。
5. 在組員的施工圖文件（`db-organization-plan.md`）裡更新了進度，註明哪些步驟做完了、卡住的問題是
   怎麼解的，方便之後接手的人查閱。

目前準備好、等確認後就會送出（commit）的檔案：
- 新的資料庫設定檔（定義那 9 個新欄位）—— **還沒套用到資料庫**
- TDX 匯入程式的小修正（補傳郵遞區號）
- 入庫核心程式的修改（新增 9 個欄位的寫入邏輯）
- 施工圖文件的進度更新

### 6. 補做沒有自動測試覆蓋到的驗證

寫完上面那些改動後，發現一個既有的盲點：負責「把資料真正寫進資料庫」的那段核心程式
（`ingestToDB`），repo 裡從頭到尾都沒有任何自動測試碰過它——之前跑的 58～98 項測試都只測到
「資料怎麼清洗」那一層，沒測到「清洗完的資料怎麼組裝、寫進資料庫」這一層，而這次新增的 9 個欄位
邏輯剛好就長在這一層。

因為這時發現 Supabase（資料庫）連不上（見下方說明），沒辦法直接拿真資料庫測試，所以改用「假裝
資料庫」的方式驗證：寫一支臨時腳本，攔截掉真正會送網路請求的兩個地方（寫入資料庫、呼叫 Gemini
算向量），改成接住資料、印出來看，這樣完全不用連線到 Supabase 或花費 API 額度，純粹確認「程式邏輯
本身對不對」。

測試結果：分別模擬「TDX 來源」和「手寫 45 筆來源」兩種情境送進去，9 個新欄位、以及原本的
`metadata` 欄位都跟設計時預期的結果完全一致，沒有任何一個欄位算錯。驗證完就把臨時腳本刪掉了，
沒有留在 repo 裡。

⚠️ 沒辦法用這個方式測到的部分（一定要等 Supabase 連線恢復才能驗證）：
- 資料庫設定檔（新增 9 個欄位）真的套用到資料庫時會不會出錯
- 真的寫進資料庫後，欄位內容讀出來是否跟預期一致

### 7. 發現 Supabase 連不上，而且比「休眠」更嚴重

原本以為 Supabase 只是免費方案自動休眠（重新打開後台喚醒一下就好），但實際檢查發現：
**這個資料庫網址連 DNS 都解析不出來**（用 Google 的公開 DNS 查也是「查無此網域」），這跟「休眠」
是不一樣的狀況——休眠的話網址通常還能連到、只是回應比較慢或顯示「已暫停」的訊息；現在這種「連
網址都不存在」的狀況，比較可能是**專案被刪除了，或是網址已經換掉了**。

這個需要有 Supabase 後台管理權限的組員盡快去確認狀況，不是單純「喚醒」就能解決，可能要重新建立
專案或找到正確的新網址。在這之前，所有需要寫入/讀取資料庫的工作（包括上面提到的 P0/P1/P2 查證
資料寫入、TDX 資料正式匯入、新欄位套用）都會卡住。

## 第三部分：對照教授 6/3 的講評，我們做得如何

教授 6/3 聽完報告後，給了幾個重要評語。整理成白話，對照我們上面做的事情，現況是這樣：

### 跟教授建議方向一致、而且已經在做的部分

- **教授說**：「你應該很用力的去收集，你有很多 Agent 去檢查它是不是可信」。
  **我們做的**：上面第一部分的官網/PTT/YouTube 三個查證管道，就是在做這件事——用好幾個獨立的
  小工具去交叉比對同一個景點，確認資料是真的。方向完全對。
- **教授說**：「你現在只有 45 筆，之後變成好幾萬筆有沒有問題？」
  **我們做的**：第二部分接上 TDX 政府資料，就是在回應這個問題——TDX 本身是全台等級的官方資料，
  理論上可以把景點數量從 45 筆擴大到幾千甚至上萬筆。而且我們也真的跑過真資料、發現並修正了
  裡面的髒資料問題（縣市寫錯、分類缺漏等），不是只有空想。
- **教授說**：「別包山包海，找一個施力點去加碼認真做」。
  **我們做的**：最近這段期間，地圖美化、App 介面、PWA 安裝圖示這些功能都先暫停，所有力氣都
  押在「景點資料可信度」跟「資料庫整理」這條線上。等於是已經自然而然在收斂了，只是還沒有正式
  跟教授講清楚「我們選的施力點就是這個」。

### 教授有提到、但我們目前還沒處理到的部分

- **在地端部署 LLaMA**：教授提到應變系統未來要在自己的伺服器上跑一個 LLaMA 模型，但目前
  系統還是用 Gemini／Claude 這種雲端 API，完全沒有人開始做本地部署這件事。這個問題目前還
  懸在那邊沒有人認領，需要組內討論：到底要不要做？如果改變主意不做了，也要講清楚原因。
- **KKday／Klook 導購抽成**：之前有寫過一份規劃文件，但後續沒有人真的把「串連 KKday/Klook
  連結、抽成試算」這件事做出來，目前還只是停在文件階段，沒有變成真的功能。
- **模組之間「整合故事」講不清楚**：教授覺得我們「景點驗證」「應變系統」「使用者介面」感覺是
  各做各的（他形容成「道家」，各自為政）。技術上這幾塊其實有串起來（應變系統會去查詢景點
  資料庫），但目前沒有人特地去畫一張清楚的圖、講清楚「資料是怎麼從驗證一路流到使用者看到的
  畫面」，這件事還沒做。
- **真的證明「擴大規模也不會出問題」**：雖然接上了 TDX，但目前還只是小量測試（抓個幾筆資料
  跑跑看），還沒有真的一次匯入大量資料、拿實際數字（例如「成功匯入 500 筆，成功率多少%」）
  去回答教授「幾萬筆會不會出包」的疑慮。
