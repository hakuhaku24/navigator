## 第一部分：多來源資料「衝突」不再靠猜，正式有規則可循（7/2）

**要解決的問題**：同一個景點，Google／OSM／部落格／TDX 政府資料講的可能不一樣（地址不同、營業時間
不同、甚至「還有沒有開」都兜不起來）。教授 6/3 那次課後、7/1 又再次提到：不要硬選一個答案交差，
要讓系統知道「這裡有衝突」，能澄清就澄清，不能澄清就誠實地把多個版本都留著。

### 1. 寫了一套「兩步驟」衝突判斷邏輯

- **第一步：能不能澄清？** 如果兩個來源的「可信度層級」差距夠大（例如官方資料 vs. 部落格），或者
  同層級但一個資料明顯比較新（差超過 30 天），系統就直接採用比較可信的那個版本，不用讓使用者自己
  判斷。
- **第二步：真的沒辦法分出高下，就讓多個版本並存**，不會硬湊一個「看起來最像對的」答案出來騙自己。
- 這套邏輯目前套用在四個欄位：官方名稱、地址、營業時間、是否營業中。

### 2. 把 TDX 政府資料正式當作「最可信的一層」加進來

- 景點名稱如果 TDX 有登記，優先採用（因為是政府資料，可信度視為一年內都還算新）。
- 地址、營業時間也會參考 TDX，但可信度沒有「名稱」那麼高，而且營業時間這種容易過期的資訊，系統
  設計成「比較快忘記」（60 天內沒更新就會被視為過時）。
- 唯獨「現在是否營業中」這個欄位，刻意選擇**不採用** TDX 的說法——因為測試時發現 TDX 在這個欄位上
  常常是錯的（下面會解釋）。

### 3. 拿全部 45 筆景點資料實測，結果誠實記錄下來

- 45 筆裡面，**32 筆確實有資料衝突、13 筆乾淨**（各來源講的都一樣）。
- 測試過程中抓到幾個很有意思的真實案例，值得讓全組知道：
  - 有一筆資料是 OSM 系統「認錯地方」，把別的地點資訊誤植到我們的景點上。
  - 有一筆是因為繁簡體／異體字寫法不同，系統一度誤判成「兩個不同的名稱」。
  - 有一筆刻意示範「如果照單全收 TDX 資料會出什麼問題」，證明「該相信哪個來源」不能一律套用同一個
    規則。
  - 「是否營業中」這個欄位特別容易出現「假陰性」（明明有開，資料卻顯示沒開），這也是上面決定不採用
    TDX 這個欄位的原因。
- 完整測試報告見 `agents/poi-verifier/tests/conflict-resolver-report.md`（測試報告後來從根目錄搬到
  `tests/` 資料夾，並統一改成小寫檔名，跟同資料夾其他報告命名方式一致，純粹是整理，沒有邏輯變動）。

### 4. 順手把「教授 7/1 回饋清單」的完成狀態記錄下來

新增了 `待討論並完成部分_0702.md`，把教授 7/1 那次課提的四條建議逐一標註目前狀態（哪些做完了、哪些
還要等大家開會拍板才能動工），方便之後回頭對照，也提醒大家「有些 .md 文件可能已經過時，DEVLOG.md
才是最新進度的可信來源」。

## 第二部分：把「資料有分歧」這件事，做成使用者看得懂的畫面（7/5）

第一部分做完的是「後端知道哪裡有衝突」，但教授要的是**讓使用者也看得到**——不是偷偷解決掉，而是
透明呈現「這個景點的資料，不同來源講的不一樣，我們是怎麼判斷的」。

### 1. 離線把 45 筆資料的衝突分析算好，存成一份檔案

- 新增一支腳本 `generate-frontend-conflicts.ts`，把第一部分算好的衝突結果重新跑一次、輸出成
  `poi_conflicts.json`。**注意**：這支腳本不會呼叫任何外部 API（不用 Google/YouTube/Gemini），純粹
  是把已經查證過的資料重新整理格式，所以不會多花任何一分查證成本。

### 2. 把衝突資料併進前端讀得到的資料庫檔案

- 原本組出 `poi-kb.ts`（前端拿景點資料用的檔案）的程式 `gen-poi-kb.js`，現在多合併一份
  `conflicts` 欄位進去。
- 過程中順便修掉一個潛在的 bug：組資料的程式原本假設檔案是用一般換行符號寫的，但 `pois.ts`
  這個來源檔案其實是用 Windows 的換行格式（CRLF），沒處理好的話某些內容會解析失敗。這次一併修正。

### 3. Explore 頁面（景點探索頁）新增「資料分歧」的視覺呈現

- 卡片上：只要這個景點有任何欄位資料不一致，就會出現「⚠ 資料分歧」的橘色徽章提醒使用者。
  （實測跟後端測試報告的「32 筆有衝突」數字完全對得上。）
- 點進景點詳情：新增一個「來源資料不一致」的區塊，把每個有分歧的欄位攤開來給使用者看——
  最後採用的是哪個版本、是怎麼判斷出來的（只有一個來源／大家講的都一樣／靠可信度層級分出高下／
  靠資料新舊分出高下／真的沒辦法分只好並存），以及每個來源原本各自講了什麼、來源等級是官方、
  半官方、部落格還是使用者回報。
- 這部分做完後有實際跑過型別檢查和建置流程確認沒有壞掉，也用開發伺服器實際看過畫面確認徽章數量
  正確。

### 4. 把「待討論並完成部分_0702.md」的建議一狀態更新成「前後端皆完成」

因為這兩天做完的就是教授建議一（多來源衝突要並存、透明呈現）剩下的前端那一半，所以回頭把 7/2 那份
文件的狀態改成「後端＋前端已完成」，這一項不用再排進會議討論。

### 5. 新增「待討論事項_0705.md」——把「真的會卡住專案」的事挑出來排序

隨著待辦事項越堆越多，容易分不清楚「單純還沒空做」跟「不討論、不拍板全隊就會卡住」。這份新文件
把懸而未決的事項依「卡住程度」分成四級（P0 全隊卡住／P1 卡前端或後端下一步／P2 需要共識但不急／
P3 可各自並行處理），並附上建議的會議流程，讓下次討論可以聚焦在真正該拍板的事情上，不用每件事都
從頭吵一遍。

## 第三部分：讓 LLM 真正查得到我們驗證過的景點資料，後端接口先做起來（7/6）

這是回應教授另一條回饋：「使用者端呼叫 LLM 的時候，那個 LLM 到底有沒有真的讀到我們辛苦驗證好的
POI 資料？」——如果只是直接呼叫 Gemini，模型是不會自動知道我們資料庫裡有什麼的，必須靠 RAG
（先用語意搜尋把相關資料找出來，再塞進提示詞給 LLM 看）才有辦法。

### 1. 之前 RAG／混合搜尋只活在後端 agent 內部，這次正式接成前端能呼叫的 API

- 新增 `src/app/api/poi/search/route.ts`，開了兩個對外端點：一個給完整參數的正式查詢
  （POST），一個給簡單快速查詢用（GET）。
- 新增 `src/lib/poi-search.ts`，把「先用 Gemini 把使用者的搜尋字句轉成向量」＋「呼叫資料庫做
  混合搜尋（語意 ＋ 關鍵字一起找）」＋「用結構化條件加權排序（Structural Boost，例如符合地區、
  室內外需求的景點排前面）」這幾個步驟串起來，變成一個可以直接被前端呼叫的功能。

### 2. 小修：explore 頁面的來源色塊補齊

之前「資料分歧」徽章詳情面板已經會顯示官網／YouTube／PTT 這三種來源，但畫面上的顏色標籤設定
（`SOURCE_LABEL` / `SOURCE_COLOR`）漏了這三種，會顯示不出中文名稱跟對應顏色，這次順手補上。

### 3. 更新 CLAUDE.md 的「當前進度」章節

把第 9 節（進度總覽）改成反映 Phase 2（Agent 核心實作）已完成、Phase 3（前後端整合）進行中的
現況，並更新第 10 節的檔案路徑指引。

⚠️ **這次只做完「後端接口」，不代表教授的問題已經解決**：目前前端還沒有任何畫面真的去呼叫這個新的
搜尋 API，「使用者最後在畫面上會看到什麼、LLM 回答要不要附上引用來源／信度標示」這件事還沒設計、
也還沒決定。這部分已經記錄在 `待討論事項_0705.md` 的第 4 項，需要討論後才能繼續往前做，避免前端
先做了才發現跟後端接口對不上。
