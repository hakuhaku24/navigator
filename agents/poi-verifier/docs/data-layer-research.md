> 版本：v1（內部知識整理，知識截止 2026-01）

> 對象：Navigator（台灣多人旅遊規劃 App，Gemini 768 維 embedding + Supabase pgvector，計畫擴台）

---

## 摘要（先看這段）

1. **進階 RAG（Agentic/MCP）不該現在上**：對「以結構化 POI 為主」的系統，Basic RAG + metadata 過濾 + **hybrid 檢索 + rerank** 的 CP 值遠勝 multi-hop。進階能力只該放在「即時應變」決策。
2. **embedding 維度**：768 對 demo 夠用；擴台後值得用真實資料 benchmark 768 vs 1024(BGE-M3) vs 1536。中文要特別測**繁中/台灣在地用語**。
3. **pgvector 擴台沒問題**：數萬筆是小資料；真正該補的是 **hybrid search（向量+全文）+ reranking**，而非換 DB。
4. **可信度最大缺口 = 即時層與回饋迴路**：交通/歇業還是 mock；沒有使用者回饋學習。應接 **TDX 運輸資料、觀光署開放資料**等官方即時源。
5. **要「真實又好用」**：資料來源要補官方即時源、驗證要自動化再驗（freshness）、檢索要 hybrid+rerank、並建立使用者回饋迴路把「賦能」階段補上。

## 1. 進階 RAG 架構：對 Navigator 划不划算

| 架構 | 核心 | 對 Navigator 效益 | 成本/風險 |
|---|---|---|---|
| **Basic RAG**（現況）| embedding→向量檢索→LLM | POI 是短結構化記錄，這就夠 | 低；確定性、好測試 |
| **Structured RAG** | 依文件章節層次切片 | 只適合**長文件**（架構書）；POI 不適用 | 已有 `structured-rag-demo.ts`，定位正確 |
| **MCP + RAG** | AI 即時連外部源 | 對**應變模組**有價值（即時天氣/交通）| 中高；2–3 源用普通 API 呼叫即可達 80% 價值 |
| **Agentic / Multi-hop** | AI 自主多步檢索 | 複雜多條件規劃品質↑ | 最高；非確定性→難測試、難穩定 demo、可信度反降 🔎 |

**結論**：檢索層保持 Basic RAG（便宜、可信、可測），把 agentic 智能集中在 **Strategy Agent 的 Swap/Switch 決策**。這也符合教授「深入 2–3 模組、別過度複雜」的方向。

> 近期業界趨勢（待查證 🔎）：2024–2025 「Agentic RAG」很熱，但生產系統普遍回報**可靠性與成本**是主要痛點，多採「Basic 檢索 + 在決策層加 agent」的折衷，與本案判斷一致。

## 2. 中文語意檢索的 embedding 模型

| 模型 | 維度 | 中文 | 特點 |
|---|---|---|---|
| **gemini-embedding-001**（現用）| 3072（MRL 可降 768/1536）| 佳 | task-type 配對、免費額度大 |
| OpenAI text-embedding-3-large | 3072（MRL 可降）| 佳 | MRL 截斷實證最完整 🔎 |
| **BGE-M3**（BAAI）| 1024 | **強** | **內建 dense+sparse+multi-vector（等於自帶 hybrid）**、可本地部署免 API 費 |
| bge-large-zh-v1.5 | 1024 | 中文 SOTA（較舊）| 純中文場景穩 |
| Cohere embed v3 multilingual | 1024 | 佳 | 商用、rerank 生態完整 |
| jina-embeddings-v3 | 可變(MRL) | 佳 | 多語、長文 |

**維度 vs 召回的權衡（重點觀念）**
- **Matryoshka（MRL）**：可直接截斷維度，品質損失極小（OpenAI 實證：large 截到 256 維仍勝舊 ada-002 1536 維 🔎）。
- **「低維分離度較好」要修正一個說法**：你們 45 筆實測 768 比 3072 分離度好（14.6% vs 12.9%），這在**小樣本**成立；但**規模變大、概念變密時，高維通常對召回有利**。所以擴台別預設 768 最佳——要 benchmark。
- **繁中/台灣用語陷阱**：多數多語模型訓練語料**簡體佔多**，繁中與台灣在地詞（如「IG 打卡」「網美」「親子友善」）表現可能弱化 🔎。**務必用你們真實 query 測**，別只看 MTEB 英文榜。

**建議**：擴台時用真實台灣 POI + 真實使用者 query，跑 **gemini(768/1536) vs BGE-M3(1024)** 一輪，比召回率+分離度+成本。BGE-M3 額外吸引力是**自帶 hybrid**、可自架省 API 費。

## 3. pgvector 擴展實務

**規模**：數萬筆對 pgvector 是小資料（它能撐百萬級）。換 DB 不是現在的問題。

| 索引 | 適用 | 注意 |
|---|---|---|
| **HNSW**（現用）| 召回/延遲最佳、寫入自維護 | 參數 `m`(預設16)、`ef_construction`(64)；查詢期 `ef_search`(40) 可即時調高換召回 |
| ivfflat | 記憶體較省、建得快 | 需先有資料訓練 lists；召回看 lists/probes |
| **halfvec** | >2000 維或想省一半空間 | fp16、HNSW 支援到 4000 維；召回幾乎不損 |

**真正該補的兩件事（效益 > 換維度）**
1. **Hybrid search（向量 + 全文/BM25）**：純向量對「**精確景點名、罕見詞、地名**」弱。加 Postgres 全文檢索（`tsvector`）或 ParadeDB/pg_search（真 BM25），用 **RRF（reciprocal rank fusion）**合併兩路結果。對你們 S07「精準命中」這類查詢提升明顯 🔎。
2. **Reranking**：向量召回 top-20 → 用 cross-encoder reranker（bge-reranker / Cohere rerank / jina）重排取 top-5。**精度提升通常是各手段裡最大的**，45 筆成本可忽略 🔎。

> 對應你們之前的觀察：分數「擠在 65–75%」靠調維度只能緩解，**rerank 才是根治**——它用語意更細的模型重新打分，把真正相關的拉開。

## 4. POI 資料可信度與時效性

**你們已做對的**：多來源 + 四級可信度 + 時間衰減——這正是學術上的 **truth discovery / source-weighted voting** 思路，方向專業。

**業界怎麼做（待查證 🔎）**
- **Google Maps**：商家驗證（Google 我的商家）、Local Guides 群眾貢獻、用定位資料算 popular times、用 ML + 政策打假評論、靠多訊號偵測歇業。
- **TripAdvisor**：評論審核 + 詐騙偵測模型。
- **學術**：跨來源 **conflation/entity matching**（同一地點多來源對齊合併）、recency 信號做 freshness、reviewer graph 抓灌水。

**新興威脅：AI 生成假評論**——2024 後 LLM 灌評論爆增 🔎。偵測靠：發文爆量偵測（burst）、文體分析、帳號關聯圖。你們的「業配過濾」要再加這層。

**台灣可直接用的官方資料源（高價值，免費）**
- **TDX 運輸資料流通服務（交通部 MOTC）**：即時公車/捷運/台鐵/高鐵/路況 API——**直接補你們「交通應變還是 mock」的缺口** 🔎。
- **觀光署 觀光資訊資料庫 / data.gov.tw**：官方景點開放資料（可當 P0 級來源）🔎。
- **中央氣象署 CWA 開放資料**：已用。
- 各縣市政府開放資料平台。

## 5.（重點）資料獲取缺口 + 「真實又好用」的落地建議

### 現況缺口盤點

| 面向 | 現況 | 缺口 |
|---|---|---|
| 即時性 | 只有天氣（CWA）| ❌ 交通/路況/歇業仍 mock |
| 來源 | 6 來源（含官網/PTT/YT）| ❌ 缺**官方即時源**（TDX、觀光署）、Google 評論情緒 |
| 檢索品質 | 純向量 768 | ❌ 無 hybrid、無 rerank |
| 時效維護 | 一次性驗證 | ❌ 無**排程再驗證 / staleness 監控** |
| 去重合併 | 各來源獨立 | ❌ 無跨源 conflation（同景點多來源未合併）|
| 使用者回饋 | 無 | ❌ 五階段方法論的「**賦能**」未實作 |
| 可信度透明 | 內部有分數 | ❌ 未對使用者呈現「為何可信」 |

### 分優先級建議

**P0（直接決定「真實」與「好用」，先做）**
1. **接 TDX 即時交通 API**：把應變從 mock 變真實——這是 Navigator 差異化（即時韌性）的命脈。
2. **接觀光署開放資料當 P0 來源**：官方景點資料拉高可信度基線、也是擴台補量的主力。
3. **檢索加 rerank**：召回 top-20 → reranker → top-5。性價比最高的品質提升。

**P1（擴台前要有）**
4. **跨源 conflation/dedup**：同一景點從多來源合併成單筆，避免重複與衝突。
5. **Hybrid search**：向量 + 全文，修「精確名/地名」檢索弱點。
6. **freshness 自動化**：排程定期重驗（依 time-decay 觸發），標記過期資料。

**P2（長期，補完方法論）**
7. **使用者回饋迴路**：收集投票/veto/實際選擇 → 回灌偏好（「賦能」階段）。
8. **可信度對使用者透明**：卡片上顯示「資料來源 × N、最後驗證 X 天前」，把信度變賣點。
9. **AI 假評論偵測**：在業配過濾上加文體/爆量偵測。

### 一句話策略
> **真實 = 官方即時源（TDX/觀光署）+ 自動 freshness；好用 = hybrid+rerank 的精準檢索 + 即時應變 + 回饋學習。** 不是靠更潮的 RAG 架構，是靠把資料「接得即時、驗得持續、找得精準、學得會」。
